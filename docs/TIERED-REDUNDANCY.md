# Tiered Redundancy — limp mode to hyper processing

**Status: Zak's framing, recorded 2026-11-18. UNGRADED —
a doctrine note, companion to QUBIT-ATMOSPHERE.md (that
note covers how a system is set up; this one covers why
a system persists).**

## The framing (Zak's words, lightly ordered)

The redundancy is important for autonomous AI, or robots
with agency. Our system has tiers that protect the logic
and function relevantly: at the lowest tier this could be
limp mode, up to hyper processing for AI robotic agency.
And future automation survival and viability.

## What it means in the stack as built

The tiers are not a performance ladder. They are
redundancy with the logic protected at every level, so
function never goes binary — a system that can only be
fully on or fully dead does not survive contact with the
real world; a tiered one sheds capability and keeps its
core. Limp mode is the floor's name: reduced function
that preserves the essential logic — get home, stay safe,
keep the core promise — instead of failure.

Instances from the classical build, each the same move
(drop a tier, keep the function):

- the governor throttles dwell under storage/RAM/load
  pressure instead of letting it fight the user for the
  machine — and logs the skip rather than hiding it
- the mic walk falls through every capture path until
  one hears; a muted server is named, never mistaken
  for a dead mic
- clips degrade to stills; stills degrade to levels;
  the patrol degrades, it does not stop
- the smallest hardware pairs its model as a nominal
  seat and the script floor (web search, system state)
  carries the experience — the floor is a function,
  not an absence

## Refinements (Zak, 2026-11-18, later the same day)

**Mid falls to limp, and limp is the best low config.**
The medium tier falls back to limp mode in the worst
cases — and limp mode should be the best low-tier
configuration, functional, able to move logically, even
just to message for a hard reset or an update. The floor
is not a crippled version of the tier above it; it is the
best version of the tier below it, and it always keeps a
communications path out.

**Low tiers hold the whole range; the profile evolves.**
Low tiers should have the whole range if new components
attach — the profile is persistent and evolving, not
fixed at install. A small system that gains a camera, a
mic, memory, or a node climbs; what the user chose
persists while what the machine IS keeps being re-read.

**The SOS minimum.** No small system just locks up or
spits stupid error codes. Logic should still stream, or
message, failure code snippets — a failure is a
communication, in usable form, or it is a second failure
on top of the first.

The SOS minimum is a running logic thread of its own
that the watchdog updates. If the watchdog ever can't —
or a fix request has been ignored — the SOS fires,
backed by the watchdog loop's log of the most recent
failed state and its needs for realignment. (Built the
same day: the watchdog records mode, failed state, and
realignment needs into a log every cycle; a standalone
SOS resident reads the log and fires — on the episode,
again on an escalation cadence while ignored, and on
its own if the log goes stale, quoting the last recorded
state. Separate process, separate unit: the call for
help does not share the watchdog's fate.)

## The agency extension

For a robot, the tiers meter agency itself, not just
processing. Hyper processing at the top: full planning,
parallel tasks, real discretion. As tiers fall away,
agency contracts toward survival functions — move safely,
signal, preserve state, wait for better conditions. The
redundancy is what makes the agency trustworthy: the
fallback is designed, not improvised. Survival and
viability are not features added later; they are what
the tier structure is.
